# Generated id columns for new tables

## Goal

A new table starts with an `id` column that the database generates, so the user does not rebuild the same primary key every time. What the new table starts with is a preference the user controls from the toolbar: an auto-incrementing integer (the default), a generated uuid, or no id column at all.

## Behavior

- Creating a table with the preference on `integer` or `uuid` also creates a column named `id`: that type, `NOT NULL`, the table's primary key, and **generated**. With `none` the table starts empty, as before.
- Any `integer`, `bigint` or `uuid` column can be marked **Auto-generate** in the inspector. Changing a generated column to another type clears the mark.
- In the DDL (PostgreSQL), a generated `integer` or `bigint` column gets `GENERATED BY DEFAULT AS IDENTITY`, and a generated `uuid` column gets `DEFAULT gen_random_uuid()`. The clause follows `NOT NULL`:

  ```sql
  CREATE TABLE "users" (
    "id" integer NOT NULL GENERATED BY DEFAULT AS IDENTITY,
    "name" text,
    PRIMARY KEY ("id")
  );
  ```
- The preference is an app setting stored under its own key (`forge:settings`), not in the project file: it applies to every project and survives "Start a new project". It only affects tables created afterwards.

## Decisions

| Decision | Choice | Rejected |
|---|---|---|
| Auto-increment in SQL | `GENERATED BY DEFAULT AS IDENTITY` | `GENERATED ALWAYS`, `serial` |
| Generated uuid | `DEFAULT gen_random_uuid()` | uuid without a default |
| Where the preference lives | Its own `localStorage` key | Inside the project |
| Selector options | integer, uuid, none (default integer) | integer and uuid only |

## `@forge/core`

- `Column.generated?: boolean`. Absent means false, so saved projects stay valid and `formatVersion` does not change.
- `GENERATED_COLUMN_KINDS = ['integer', 'bigint', 'uuid']`.
- Validation: a column with `generated: true` and another type is the issue `generated-unsupported-type` (a draft with it can be saved; the DDL is refused).
- `Dialect.generatedClause(type): string | null`; PostgreSQL as above.
- `generateDdl` appends the clause after `NOT NULL`.
- `parseProject` accepts `generated` absent or boolean and rejects any other value, with its path.

## `apps/web`

- `AppSettings { newTableId: 'integer' | 'uuid' | 'none' }`, default `integer`. `loadSettings(storage)` never throws and falls back to the default for a missing, unreadable, malformed or blocked value; `saveSettings(storage, settings)` never throws.
- The store holds `settings` and `setNewTableId`; `addTable` creates the id column from them.
- Toolbar: a select labelled "New tables start with" (`id: integer (auto-increment)`, `id: uuid (generated)`, `no id column`). Inspector: an "Auto-generate" checkbox on integer, bigint and uuid columns. Table node: an `auto` badge on generated columns.

## Testing

Core unit and integration tests for the rule, the dialect clause, the generator and the parser (including a project saved before this change). Web unit tests for the settings, the store, and the type-change helper. The Playwright suite runs with the preference on `none` by default, and gains a spec for the new behavior; the guided tour uses uuid ids.

## Acceptance criteria

1. A new table gets an `id` column (integer, auto-increment, primary key) by default.
2. The toolbar select switches between integer, uuid and none, and the choice persists across a reload and a new project.
3. The DDL shows `GENERATED BY DEFAULT AS IDENTITY` for integer and `DEFAULT gen_random_uuid()` for uuid.
4. The inspector toggles Auto-generate; an unsupported type clears it.
5. A project saved before this change still loads.
6. Lint, typecheck, all tests, the build and the e2e suite pass.
