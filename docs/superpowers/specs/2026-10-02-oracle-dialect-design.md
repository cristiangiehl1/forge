# The Oracle dialect

Status: approved in conversation, awaiting written-spec review.

## Intent

The same diagram generates DDL for PostgreSQL and for Oracle. The Oracle script follows the conventions of the team's own migrations (`sistema-recrutamento-selecao`, `apps/api/src/infra/database/oracle/migrations`): upper-case unquoted names, identity primary keys, named constraints, `CHECK` constraints for what Oracle has no type for. What Oracle does not have is adapted, and the adaptation is reported; only what Oracle really refuses blocks the script.

Decisions taken with the user:

1. **Target:** Oracle 12.2 or newer (identity columns, `IS JSON`, names up to 128 bytes). No 11g, no 23ai-only features.
2. **Names:** upper case and unquoted when the name is a plain identifier that is not an Oracle reserved word; otherwise quoted with its exact text.
3. **The dialect belongs to the project** and is saved with it (`dialect`, default `postgres`), plus `options` (`uuid`: `raw16` default, or `varchar36`). Projects saved before are PostgreSQL.
4. **Compatibility notes** instead of failures: `generateDdl` also returns `notes`, shown in the DDL panel.
5. **Import SQL stays PostgreSQL-only**; the dialog says so when the project is Oracle.

## Type mapping

| Forge | Oracle |
|---|---|
| `integer` / `bigint` / `smallint` | `NUMBER(10)` / `NUMBER(19)` / `NUMBER(5)` |
| `numeric(p,s)` | `NUMBER(p,s)`; precision over 38 becomes `NUMBER(38,s)` + note |
| `varchar(n)` | `VARCHAR2(n)`; over 4000 becomes `CLOB` + note |
| `char(n)` | `CHAR(n)`; over 2000 becomes `CLOB` + note |
| `text` | `CLOB` |
| `boolean` | `NUMBER(1)` + `CONSTRAINT CK_<TABLE>_<COLUMN> CHECK (<COL> IN (0,1))` |
| `uuid` | `RAW(16)` (generated: `DEFAULT SYS_GUID()`) or `VARCHAR2(36)` (generated: the hyphenated lower-case `SYS_GUID()`) |
| `timestamp` (an instant) | `TIMESTAMP WITH TIME ZONE` (generated: `DEFAULT SYSTIMESTAMP`) |
| `timestamp` without zone | `TIMESTAMP` |
| `date` / `time` / `interval` | `DATE` / `INTERVAL DAY(0) TO SECOND(0)` / `INTERVAL DAY TO SECOND` |
| `json` | `CLOB` + `CHECK (<COL> IS JSON)` |
| `real` / `double` | `BINARY_FLOAT` / `BINARY_DOUBLE` |
| `bytea` | `BLOB` |
| array | `CLOB` + `CHECK (<COL> IS JSON)` + note (the array is stored as a JSON array) |
| enum | `VARCHAR2(n)` (the longest value) + `CHECK (<COL> IN ('A','B'))`; no `CREATE TYPE` |
| domain | its base type, with its default and `NOT NULL` repeated on each column; no `CREATE DOMAIN` |

Generated integers: `GENERATED BY DEFAULT ON NULL AS IDENTITY`.

## Script shape

- `CREATE TABLE`: the columns, then `CONSTRAINT PK_<TABLE> PRIMARY KEY (...)`, then the foreign keys (`CONSTRAINT FK_<TABLE>_<COLUMN> ...`), then the `CHECK` constraints. A column is written `NAME TYPE [DEFAULT x | GENERATED ...] [NOT NULL]`: the default comes before `NOT NULL`, and `NOT NULL` is left out for primary-key and identity columns, which already have it.
- Then `CREATE [UNIQUE] INDEX`, then `COMMENT ON TABLE/COLUMN`, as for PostgreSQL. No `ALTER`, no blank line inside a statement.
- Constraint names are made unique and cut to 128 bytes, as for PostgreSQL's 63.

## Notes and blocking issues

Notes (do not block; each cites its table and column or index):

- array column stored as JSON in a `CLOB`;
- `hash`/`gin`/`gist` index created as an ordinary index;
- an index on a column stored as `CLOB`/`BLOB` is not created;
- `varchar`/`char` too long for Oracle became a `CLOB`; `numeric` precision lowered to 38;
- a raw `default` is copied as written and may be PostgreSQL-specific (`now()`, `'x'::text`).

Blocking issues (the schema cannot be written for Oracle):

- a primary key, a unique index or a foreign key over a column stored as `CLOB`/`BLOB`;
- two tables, or two columns of one table, whose names are the same once folded to upper case;
- a table or column name longer than 128 bytes.

## Core

- `Dialect` grows: `supportsUserTypes`, `constraintName`, `check`, `tableParts`, `createIndex`. The generator calls them instead of hard-coding PostgreSQL forms. The PostgreSQL output stays identical byte for byte (the existing tests guard it).
- `generateDdl` returns `notes` on success and appends `dialect.check(schema)` to the issues. `DialectNote = { code, message, tableId?, columnId?, indexId? }`.
- `oracle(options?)` builds the dialect (options change the `uuid` form); `getDialect(id, options)` picks one. The reserved-word list is part of the Oracle dialect.
- `Project` gains optional `dialect` and `options`; `createProject(schema, view, settings?)` writes them only when given; `parseProject` reads and validates them. `formatVersion` stays 1.

## Web

- The store holds `dialect` and `dialectOptions`, loads them from the saved project, saves them with it, and keeps them out of the undo history (they are neither schema nor positions).
- Toolbar: a **Dialect** select; with Oracle chosen, an **Oracle uuid** select.
- The DDL panel generates with the project's dialect and lists the notes under its buttons; Copy and Download are unchanged.
- The import dialog says that scripts are read as PostgreSQL when the project is Oracle.

## Testing

Unit: reserved words and name folding, each type, the generated clauses, `NOT NULL` and `DEFAULT` order, constraint names, notes, blocking issues, and a whole Oracle script compared with its expected text; PostgreSQL unchanged; `parseProject`/`createProject` with and without the new fields. e2e: switching to Oracle shows the Oracle script and the notes; the uuid option changes the column; the choice survives a reload; the import dialog's warning; the downloaded file is the Oracle script.

## Out of scope

Reading Oracle SQL; `ON DELETE` actions (the model has none); the `KONTRATA_` prefix (write it in the table name); Oracle 11g; 23ai features (native `BOOLEAN`, `JSON`, domains); partitioning, tablespaces, storage clauses.
